Recap of Engineering Decisions & Final Architecture
We systematically dissected a heavy-duty, local-first context and memory pipeline designed to operate seamlessly across 7 distinct repositories, 3 target APK builds, and multiple devices, avoiding model orchestration drift.
________________
1. The Path Taken & Critical Pivot Decisions
* Dumping the Overreach (OB1 vs. Custom Stack): We initially explored OB1, but bypassed it due to its intrusive, "big dick" orchestration style. Like Claude’s native tools, it attempts to hijack prompts and inject heavy execution guidelines.
* The Unified In-Repo Solution: You chose to place every single persistent asset and file system directly within the repositories under a local .agent/ control folder. This guarantees that your entire AI state is 100% version-controlled, portable, and natively carried across hardware by your existing GitSync loop.
* The Cognitive Firewall (Trapping Hermes & Claude Code): Instead of allowing the LLM to dictate tool use, we established a mandatory, hardcoded protocol chain. Hermes sits above OmniRoute as the macro planner, but is forced to route every tool query through it. Claude Code is stripped of autonomy and used strictly downstream as a high-speed Builder Tool / Code Monkey.
* The Database Engine (Local PostgreSQL with SHA-256 CAS): To prevent cross-repo data bloat from text logs and code snippets, we bypassed flat file limitations and built a centralized, local PostgreSQL database utilizing a Content-Addressable Storage (CAS) pattern.
________________
2. Final Component Mapping Inside Your Repositories
Every workspace repository is now structured to isolate tool execution states inside .agent/, linking metadata directly back to your Main Corpus Repo via MAPmd blueprints and manifest JSONL pointers:
* Mem0: Handles dynamic, rapid episodic interaction and conversation history logs.
* Terrestrial Brain: Connects your local repo workspace straight to your central, machine-local PostgreSQL engine over system sockets.
* code-review-graph: Leverages native Tree-sitter binaries to track and cache cross-repo AST code definitions local to the directory.
* Graphify: Translates codebase topology maps directly into your visual Obsidian Desktop client and Notebook-LM inputs as clean Markdown and JSON.
* ReasoningBank: Functions as your strategic quality-control supervisor. It intercepts OmniRoute’s 4 parallel data streams, strips data noise via code, and algorithmically collapses the data into a single, clean Markdown strategy card before Hermes or the builder sub-agents see it.
* Continual Harness & Task Observer: Executes the recursive code/test loops, compiles the 3 APKs, and writes the codified execution results back to the database.
________________
3. The Final Output: The PostgreSQL SHA-256 CAS Core
The crowning piece built in this session was the execution layout for your deduplicating "filing cabinet" inside your local PostgreSQL server:
1. The Master Invariant (universal_cas_store): A table where the primary key is a 64-character hexadecimal hash generated from the text itself.
2. The Context Pointer (agent_trajectories): A relational ledger tracking exactly which repo, APK build, and memory tier utilized that specific data block.
3. The Cryptographic Worker (process_cas_sha256): A native PostgreSQL PL/pgSQL database trigger using the pgcrypto extension. It automatically calculates the SHA-256 thumbprint of incoming content strings before insertion.
4. The Deduplication Invariant: Enforced via INSERT ... ON CONFLICT (sha256_hash) DO NOTHING. If multiple repositories write identical instructions or logs, Postgres drops the duplication and stores a tiny relational reference card instead.
This architecture ensures that your system stays entirely self-contained, completely local, and fully standardized against model-level defiance.
