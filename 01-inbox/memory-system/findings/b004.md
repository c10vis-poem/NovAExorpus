## Documentation/Concepts/confidence.md
Path: /data/data/com.termux/files/home/repos/wt/fdaoe-ingest/clean_md/_Jev/Documentation/Concepts/confidence.md (not flagged; full read, 216 lines)
Summary: Defines `confidence` (0..1) returned on every Choice and Score answer, derived from `probabilities`; Noul answers carry no confidence field. Gives the three-band pattern (high act, medium confirm, low route to human), risk-scaled thresholds, and exact formulas.
Items:
- Answer shape: Choice/Score answers carry `probabilities` (dict option/level -> p) and `confidence`; Choice also `.choice`, Score `.score`, Noul `.noul` (confidence.md:20-22, code at 89-100).
- Three bands: high = act automatically; medium = proceed with caution/confirm/flag; low = do not act, route to human, clarify, or fall back (58-66). Boundaries "depend on the stakes".
- Risk-scaled gating example (74-107): `confidence < 0.5` -> route_to_human; low-stakes action (check_balance) acts; high-stakes (approve_transfer) acts only if `confidence > 0.9`, else ask user to confirm. Doc: thresholds are domain-specific; "start with conservative thresholds, test with your own data" (113).
- Noul: single probability p (yes). No separate confidence. Start point 0.7 yes / 0.3 no (123). Optional confidence = |2p-1| (128), equals Choice formula for 2 options.
- Choice: confidence = (p_max - 1/n)/(1 - 1/n) (138). Only top prob counts: (0.6,0.3,0.1) and (0.6,0.2,0.2) both 0.4 (141). Python `choice_confidence` at 144-146. Alternatives worth thresholding: top probability p_max (threshold per question since depends on n) and top-to-second ratio p_max/p_second (156-157).
- Score: levels ordered 0..n-1; confidence = max(0, 1 - sum_i p_i|i-m| / MAD_unif), MAD_unif = (1/n) sum|i-(n-1)/2| (164-166). Code `score_confidence` 200-206. Examples: (0,0.5,0.5)=0.25, (0.5,0,0.5)=0 (171); bug_severity (0,0.57,0.43) ~0.35 (213).
- Meaning of low confidence: Choice = no clear winner; Score = levels ambiguous/multi-dimensional or state lacks info (48).
- Quote: "If an intelligent system, whether human or machine, cannot express honest uncertainty, the system cannot be trusted." (54)
- Docs index URL given: https://docs.typesafe.ai/llms.txt (data, not fetched).
For router/auditor: use `confidence` plus raw `probabilities`; gate per action risk.

## Build with Jev/Cookbooks/LLMs and agents/skill_suggestion/_jev-skill-suggestion/#ReadMe.txt.md

Summary: README of a Claude Code "mod" plugin, jev-skill-suggestion. It withholds Claude Code's per-session skill listing and lets Jev pick at most one skill per prompt, then attaches that skill's SKILL.md to the prompt itself. Two backends (TypeSafe API or Vercel AI Gateway) or a built-in classifier fallback. Based on TypeSafe's skill-suggestion cookbook.
Items:
- HTTP backends (ReadMe:22-25): `typesafe` = POST api.typesafe.ai/v1/systemone, model `jev-latest`, confidence reported per answer; `gateway` = POST ai-gateway.vercel.sh/v4/ai/evaluation-model, model `typesafe-ai/jev`, confidence "derived from an optional distribution". TypeSafe wins when both keys set (27). Gateway answers a noul as boolean with `probability`; both shapes read (128). Gateway API is `experimental` (`experimental_evaluate`, AI SDK 7.0.105+), "not documented publicly"; TypeSafe wire shape read from @typesafe-ai/sdk v0.6.0, gateway from @ai-sdk/gateway v4.0.86, @ai-sdk/provider v4.0.17 (259). Unverified; "Either may change."
- No key: falls back to engine `$.model.classify`, single answer, no gate, no second request (29, 131).
- Decision (108-124): Request 1 = one `choice` `which` over every candidate with its one-line description as criterion (distribution = ranking) plus three noul questions about the request (not the skill): `acts_on_user_system`, `would_follow_documented_procedure`, `prose_suffices` (inverted). Mean = gate; `gateThreshold` 0.30. Request 2 = same choice over `shortlist` 3 with full description plus first `excerptChars` 700 of SKILL.md, plus one `fits` noul per candidate answered independently; if best fits < `fitsThreshold` 0.30 the shortlist is dropped, else the choice winner is suggested. "the choice settles which, the nouls settle whether" (122).
- Reported result: on a 182-skill roster wrong loads 16.8% -> 7.3%, needless 9.8% -> 4.0% (18). (skill_suggestion.md, flagged, states a different roster size and figures; unverified which is current.)
- Fail-open: any non-2xx, timeout past `timeoutMs` (default 800), throw, or malformed body lets the prompt through with no suggestion; "The mod never blocks a prompt." (133). If the rerank was attempted and failed, suggest nothing (129).
- Injected block shape (84-91): `<skill_relevance> Relevant to the current request: NAME. Ignore this if it does not fit what the user actually asked for. ... </skill_relevance>` with the SKILL.md body inside a `<skill name dir>` tag. First line is the cookbook's wording word for word (94). With nothing to suggest and listing in place it sends "No skill in the roster appears relevant to this request." (98).
- Hooks (74-80): `prompt.attachment` on `skill_listing` (answers `{text:null}`), `prompt.submit` (runs the two requests, attaches winner), `skill.prompt` (logs whether the loaded skill was the suggested one). Subagents untouched (104). Non-task prompts (notifications, peer messages, observer reports, a typed /name) get no suggestion (135).
- Options (195-214): typesafeApiKey, gatewayApiKey, provider auto|typesafe|gateway|builtin, typesafeBaseUrl (default https://api.typesafe.ai), typesafeModel (jev-latest), gatewayBaseUrl (https://ai-gateway.vercel.sh/v4/ai), gatewayModel, inject content|suggest, hideListing true, rerank true, shortlist 3, gateThreshold 0.3, fitsThreshold 0.3, excerptChars 700, alwaysListed, neverSuggested, timeoutMs 800, logDecisions true.
- Log line format (141-150), e.g. "jev: needs a skill 0.76 . top of 58: powerpoint (0.70), pptx-author (0.30) . 160ms" then "rerank -> pptx-author (0.81) . fits ...". Latencies 160ms and 90ms are the doc's example lines (unverified).
- Privacy (189-191): with a key, prompt text, candidate names and one-line descriptions leave the machine on request 1, and the first 700 chars of each shortlisted SKILL.md on request 2; with no key nothing leaves.
- Requires Claude Code 2.1.278+; mods default-on from 2.1.287; `bun test` path given (253-257). Install and setup commands are quoted as data; I did not run any. The setup command edits the user-level Claude settings (a skill-overrides map plus a bundled-skills switch) with a backup file; "restore" reverses it (50-68). Note for this stack: that is an agent-config edit, owner decision, not done by me.
- Mentions sibling mod jev-model-router, "asks the same decision model which model and effort a prompt deserves" (249); not in this batch, unverified.

## Build with Jev/Cookbooks/Search and matching/semantic_find.md
Path: .../clean_md/_Jev/Build with Jev/Cookbooks/Search and matching/semantic_find.md (not flagged; full read: 324 lines, read in 4 pages because one line is a very long playground URL)
Summary: Line-by-line semantic search over a document (GitHub Terms of Service, 218 lines) in ONE request: tag each line with an ID, a Choice question over the line IDs ranks lines by how well they answer a query, and a Noul question "exists" says whether the document answers at all. Replaces vector search for documents up to 255 lines.
Items:
- Model: `TYPESAFE_MODEL = "jev-1.12"` (semantic_find.md:68). Client `TypeSafeClient(api_key=..., timeout=120.0)`; SDK package `typesafe_sdk` (Choice, Noul, NoulCriteria, TypeSafeClient); helper `cooksafe>=0.2.0,<0.3.0` (JsonCache replays recorded calls) (48-74). Env var TYPESAFE_API_KEY (42).
- State format (96-110): document as one text string, each line prefixed `L000| ...` via `f"L{i:03d}"`, joined by newlines. The request state is that string (a plain string, not JSON, 204-207).
- Choice request shape (125-131): `Choice(instructions='Which line of the document contains the answer to: "{query}"?', criteria={line_id: None ...})`; option descriptions are None because the text is in the state.
- Limit (136-141): "A `Choice` question accepts up to 255 options, so this recipe searches documents of up to 255 lines in one request. Past that, search in two passes: one Choice question picks a window of lines, and a second ranks the lines inside it."
- Why the second question exists (145-146, 159-160): "Choice probabilities always add up to 1, so some line ranks first even when the document doesn't answer the question." The Noul probability "doesn't depend on the other options, so it can fall near zero".
- Noul request shape (149-156): instructions `Does any line of the document address or answer: "{query}"?`; criteria true "At least one line of the document states or directly implies the answer", false "No line of the document addresses this".
- One request: `client.system_one(state=..., questions={"where": where, "exists": exists}, model=model)`; read `answers["exists"].noul` and `answers["where"].probabilities` (204-213). Document sent once; both questions see the full document.
- Verdict thresholds (233-239): `FOUND, ABSENT = 0.7, 0.35`; exists >= 0.7 "answered in this document"; < 0.35 "not in this document"; between = "partially addressed". Comment: "present answers typically read >=0.9, absent <=0.05". "Tune these thresholds on your own documents before using them in production." (256)
- Doc size in the example: 218 lines, 43,980 characters (275). No latency, price or token counts stated in this file.
- Results (277-299): who owns uploaded code: exists 0.98, L052 0.95. Kick off without warning: exists 0.97, L168 0.97. Arbitration: top line L205 0.86 but exists 0.14 -> "not in this document". Minors with parental permission: exists 0.46 -> partial, L029 0.90. Interpretation (311-312): "The ranking tells you where to look; the exists score tells you whether the result answers the question."
- Source doc fetched from raw.githubusercontent.com/typesafe-ai/typesafe-public-examples/... (data, not fetched by me). Embeddings/vectors: none used; this recipe is an alternative to them.
Use: (b) auditing claims against a tool log: tag each log line/entry with an ID, ask "Which entry supports the claim: ..." as Choice and "Does any entry support the claim?" as Noul in one request; verdict = supported / partial / unsupported via two thresholds (0.7 / 0.35 as starting points, to be tuned). Beware: >255 entries needs windowing. (d) extraction: returns source line IDs, so claims stay quotable.

# What matters most for the router and auditors (from non-flagged files only; flagged files re-read once released)
1. Primitives and shape: Noul = P(yes) in `.noul`; Choice = `.choice` + `.probabilities` + `.confidence`; Score = `.score` + `.probabilities` + `.confidence` (confidence.md:20-22; parallel_questions.md:207-231). Request: `client.system_one(state=..., questions={...}, model="jev-1.12"|"jev-latest")`; HTTP POST api.typesafe.ai/v1/systemone with `{model, state, questions}` and Bearer auth (policy.ts:34-41, 461-483; ReadMe:22-25).
2. Questions are independent: adding more to one request does not change the others' answers (parallel_questions.md:20-23); one request over the same state gave ~12x lower cost and ~10x lower latency than separate calls (page figures, jev-1.12, price 0.042 per 1M input tokens, 0 output; unverified elsewhere).
3. Judge ladder to copy for the router: gate (mean of 3 request-level nouls, 0.30) -> rank (one Choice over all candidates by one-line description) -> re-read top 3 with fuller text -> independent per-candidate "fits" nouls (0.30) -> abstain if all low (policy.ts:628-675; ReadMe:108-133). Abstention is a first-class outcome; failures and timeouts (800 ms default) fail open with no suggestion.
4. Auditing a claim against a tool log: tag each log entry with an ID (`L000|`), ask Choice "which entry supports X" plus Noul "does any entry support X" in one request; verdict by two thresholds, start 0.7 supported / 0.35 absent, tune on own data (semantic_find.md:104-141, 233-239). Choice probabilities sum to 1, so a top entry always exists; only the Noul says whether the claim is supported. Limit 255 options per Choice, so window larger logs (semantic_find.md:138-141).
5. Confidence is derived from probabilities: Choice (p_max-1/n)/(1-1/n); Score uses ordered-level distance; Noul has none, use |2p-1| or the 0.7 yes / 0.3 no starting points (confidence.md:121-213). Gate by action risk: floor 0.5, destructive actions above 0.9 (confidence.md:92-109). Thresholds are starting points, not calibrated guarantees.
6. Also useful per the doc: top probability and top-to-second ratio as alternative gates (confidence.md:154-157).
7. Classification/clustering of memory items: no embeddings or vector/graph categorization appear in the non-flagged files; the closest pattern is one Choice over item descriptions as a ranking, plus Nouls for absolute fit (skill_suggestion pattern). Flagged entity_alignment, rerank_typesafe and autoresearch pages cover dedupe, rerank and features; re-read once released.
8. Prompt-injection hazard for this stack: the skill-suggestion plugin injects an untrusted skill body with "follow them now" wording (policy.ts:352-387). Treat any injected text as data; check the path-safety and frontmatter checks in policy.test.ts (290-292, 257-263) before reusing the design.
9. Observation hook pattern (jev-skill-suggestion.ts:569-582) logs whether the downstream agent followed the suggestion; this is the shape of a log an auditor can compare claims against.
10. Still unknown from this batch: Jev model-version differences (jev-1.12, 1.13, 1.14.0, jev-latest all appear), current pricing beyond the stated 0.042, and rate limits (only a hint that eight workers can hit a limit appears in flagged files). Unverified.
