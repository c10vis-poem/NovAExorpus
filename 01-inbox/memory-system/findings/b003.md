Summary: moderate Twitch chat with one Jev request per message, three questions (a Choice category, a Noul toxic, a Noul spoiler), plain code `decide()` turns answers into hide/blur/highlight/show. Numbers from `jev-1.14.0` on 2026-10-29 (CM:68).
Jev usage items:
- SDK call: `client.system_one(state=state, questions=questions, model=TYPESAFE_MODEL)` (CM:215); answers via `response.answers["category"]`, `.choice`, `.probabilities`, `response.answers["toxic"].noul`, `response.model` (CM:216-223).

- Question shapes: `Choice(instructions=..., criteria={label: description})`; `Noul(instructions=..., criteria=NoulCriteria(true=..., false=...))`; a `Noul` may omit criteria (CM:161-187).
- State is arbitrary JSON (here `{"stream": {...}, "message": {...}}`) (CM:136-143). Questions refer to state fields in backticks, e.g. "`message.text`".
- Confidence/thresholds: toxic and spoiler hide/blur at >= 0.7 (`TOXIC_AT`, `SPOILER_AT` CM:301-302); on the sample all values were <= 0.38 or >= 0.95 (CM:287-291). Advice: check thresholds on your own data.
- Latency/concurrency: median ~0.1 s per request (CM:434-436); 29 messages, 29 requests, 8 threads (CM:327); "If you hit a rate limit, lower `max_workers`" (CM:390). Cache key = state + questions, not model (CM:64-66).
- Limits stated: "At the time this cookbook was published, Jev was trained mainly on English... answered [other languages] less accurately" (CM:440-442). Close top-two categories and Noul near 0.5 should go to review (CM:443-447). The spoiler check has no memory of progress (CM:448-453).
- Pattern: answers describe the item; rules in code can change without new requests (CM:395-430, "14 messages changed, 0 new requests").
- Relevant to auditors: a message-level toxic/spoiler classification is the same shape as "did Claude lie / shortcut".

### H2. Extraction/autoformat.md (CM 624 lines)

### H4. LLMs and agents/basic_memory.md.txt.md (CM 577 lines)
Summary: a Jev-gated per-customer memory wrapper. After each routed support ticket, a second Noul request ("gate") asks whether the request states a lasting fact about the customer; if P(yes) >= 0.5 (`REMEMBER_AT`, CM:103) the (request, answer) pair is stored; before each call the saved pairs for that customer ID are added to the state under `earlier_tickets_from_this_customer` (CM:104, 362-373). Result: 6/6 later tickets routed correctly with memory vs 3/6 without (CM:518-532). `jev-1.14.0` on 2026-10-29 (CM:91).
Items for memory layers (1):
- This is an episodic-style layer owned by the caller, not by Jev: Jev is stateless, "Each Jev request sees only the state you send it" (CM:22-23). Memory = Python dict, one list per customer id; "no size limit, no check for relevance and no expiry date" (CM:382-384). Persistence: "Replace `MEMORIES` with a database keyed by customer ID" (CM:570-571).
- Gate design: judge only what the user/support staff wrote in `request.ticket`; ignore facts that appear only in the model's own answer (CM:300-324, 389-393). Directly applicable to the owner's "write memory only when a typed gate passes" idea and to blocking self-confirming loops.
- The wrapper is defined as "a basic agent harness" (CM:44-47); two sequential requests per call (CM:73-75, 375-381); could be fan-out when the gate ignores the answer.
- Risks the doc names: memory only grows; a saved answer can repeat a mistake (CM:389-393).
- Next steps listed (CM:560-573): tune `GATE` and `REMEMBER_AT` on labelled pairs; add a relevance question to pick memories; ask whether a new memory replaces an older one and remove the old entry; persist in a DB; remember what the app did.
- SDK: `SystemOneResponse.model_validate(raw)`, `response.model_dump(mode="json")`, `answer.type` in {choice, noul, score}, `answer.score` for Score (CM:327-332, 254-261). `ask()` = `client.system_one` with model pinned and call cached.
- Mapping to owner layers: NOT mem0, OB1 or Postgres. It is a design pattern for what mem0-style episodic memory could do with a typed gate in front. Mapping is my inference.

### H5. LLMs and agents/citation_check.md (CM 363 lines)
Summary: verify an LLM's citations against the source: an ordinary string match marks missing quotes `fabricated`; surviving quotes' sections go to one Choice (`supports` / `contradicts` / `says_nothing`) -> `verified` / `contradicted` / `unsupported`; confidence < 0.8 (`AUTO_ACCEPT`) goes to a human (CM:92, 229-235). `jev-1.12` on 2026-08-16 (CM:78).
Items for auditors (2, 3):
- 8 citations of RFC 7519: 4 verified at >= 0.93, 1 fabricated by string match (no model call), 1 contradicted at 0.99, 2 unsupported at 0.27 and 0.56 -> review (CM:312-336).
- Pattern: do cheap deterministic checks first (string match), use Jev for the semantic step, route by confidence. Same shape as an auditor of "did the agent claim a thing the telemetry shows is false".
- Quote match is exact after normalisation; truncated or reworded quotes come back `fabricated` (CM:341-343).
- Call: `client.system_one(state={"claim":..., "section":...}, questions=QUESTIONS, model=...)`; answer fields `choice`, `probabilities`, `confidence`; `response.usage.input_tokens/output_tokens` (CM:259-272).
