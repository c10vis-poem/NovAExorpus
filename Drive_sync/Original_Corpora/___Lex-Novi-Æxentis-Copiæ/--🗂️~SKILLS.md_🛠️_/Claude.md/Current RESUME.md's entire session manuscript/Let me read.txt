Let me read `ARCHITECTURE.md` properly (not just the fragments I've seen) before summarizing it, and give you a grounded answer on the global-vs-per-repo question.

**What's actually in `ARCHITECTURE.md`** (9 sections, now read in full):

1. **Design principles** — 5 rules: roles are fixed but runtimes swap; markdown is the only source of truth (vector stores are just rebuildable indexes over it); audit only happens at the write boundary, not on every thought; tiers degrade gracefully when a node is missing; the auditor is structurally independent so it can't be co-opted or gamed by the thing it's judging.
2. **Node tiers (T1–T4)** — capability classes, not literal devices: T1 Edge/Mobile (phone, always-on-person), T2 Personal/Workstation, T3 Home Node (the always-on hub — this is where memory itself lives), T4 Cloud (elastic, heavy training, out-of-band audit). A role prefers a tier and falls back down the chain if that tier's absent.
3. **Agent roles** — Query/tool-exec (narrow structured work, T1→T2), Executive (heavy reasoning, T3→T4→T2), Librarian/switchboard (picks which memory surfaces, distills learnings back into the wiki — this is "the flywheel"), Auditor (independent gate, T4 out-of-band, never shares context with what it's judging).
4. **Memory** — the 4-type table we just built.
5. **Audit gate** — Tier 0 (read/reason, free), Tier 1 (reversible write, self-audit), Tier 2 (irreversible or a **memory commit** — requires an independent auditor, or queues for audit-on-reconnect if the cloud auditor isn't reachable). This is the mechanism that stops working/ephemeral scratch state from silently becoming permanent memory.
6. **ReasoningBank integration** — maps your executor/auditor split 1:1 onto Google's ReasoningBank paper (arxiv 2509.25140): the executor never calls a judge, the auditor is the reward source, a new strategy only gets minted after a passed verdict.
7. **Profiles & privacy tiers** — 4 privacy postures (Convenience/Hybrid/Max-privacy/Walled-training), each binding the Executive role to a different runtime.
8. **Component mapping** — the real repos filling each role: OpenWiki (declarative-generation), Graphify/obsidian-skills (declarative-render), OB1 (recall), reasoning-bank (strategic), notebooklm-py (synthesis tool), OmniRoute (gateway), Novus-Agenti (device client), claude-skills (skill library).
9. **Open questions** — auditor placement, shared vs separate vector backend, local embedder choice. Same 3 open decisions we already logged in `unresolved.md`.

`protocol/memory.md`'s actual job, concretely: it's just the pointer — one paragraph saying "the real table is in ARCHITECTURE.md §4, don't duplicate it here." Nothing more. If you want it to hold something substantive later (implementation-level detail: actual API contracts between the roles and each memory backend, message schemas, etc.), that would be new content, not something it currently has a stub for.

**Global vs. per-repo — this splits three different ways, not one:**

- **Skills are already global by default.** `~/.claude/skills/` is not scoped to any directory — that's exactly why `graphify`, `notebooklm`, `obsidian-vault`, `mattpocock-skills`, `android-termux-operator`, and the `aesop-voice-pipeline` skill I built tonight all work regardless of which repo or directory a session starts in. Installing ECC, graphify, obsidian-skills, ncbooklm-py-as-a-skill, "honey-for-devs" as **skills** this way gives you exactly the global persistence you're asking for. (Skills *can* also be scoped to one project instead, via a project-local `.claude/skills/` folder, but that's opt-in, not the default.)
- **Memory is the opposite — scoped per working-directory by design**, which is the whole thing we discovered earlier tonight (the rich memory store lived under `~`, this session under `~/downloads` saw none of it). There's no built-in "global memory" toggle. The practical fix is either always launching sessions from the same home directory, or accepting that memory earned in one project scope won't automatically show up in another.
- **`CLAUDE.md` has both**: a global one at `~/.claude/CLAUDE.md` (already exists, loads every session everywhere) and per-repo ones (load only when cwd is inside that repo).
- **`unresolved.md`/`RESUME.md` aren't Claude Code mechanisms at all** — they're plain files we invented for this repo's own convention. A global version could exist as a plain file, but nothing auto-loads it the way CLAUDE.md gets auto-loaded — it'd only get checked if the global CLAUDE.md explicitly said to check it.
- **Cloned repos and installed tools** (notebooklm-py, honey-for-devs, graphify-the-repo) are just directories on disk — reachable from any session via absolute path regardless of "install scope," which is exactly how I've been reaching into `~/repos/aesop-xi` all night from a session sitting in `~/downloads`.
