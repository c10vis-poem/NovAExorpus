**pypdf welds tightly-spaced figure cells**


PDFs with data tables have numbers placed very close together on the page. The PDF reader the checker uses (pypdf) sometimes sees two close numbers and joins them without a space. So `0.40` in one table cell and `0.95` in the next cell becomes `0.400.95` when pypdf reads it. The checker then looks for `0.40` as a separate value in the cleaned file, can't find it, and calls it missing. But it's not missing — pypdf garbled its own read. Not a cleaning defect.


---


**DOCX hyperlinks have no separator**


In a Word document, multiple links sitting in the same paragraph are stored in the raw XML like: `<link>first</link><link>second</link>` with literally nothing between them. The checker's XML reader sees that and runs them together: `firstsecond`. Fix was to add a newline between each link element when reading.


---


**Contiguous tail test / icon glyphs**


To confirm the end of each source made it into the cleaned file, the original test was: take the last section of the source file as one exact string, find that exact string in the cleaned file.


Icon glyphs are decorative characters — arrows, checkmarks, copy symbols — that appear in some PDFs. Two different PDF readers (the cleaner uses pymupdf, the checker uses pypdf) don't always describe the same glyph the same way. One might output a real arrow character `↓`, the other might output the text `arrow_circle_down`. Same thing on the page, different bytes in memory.


So the exact-string test fails even though the content is fine — the two readers just see the same symbol differently. The fix was to break the ending into individual words and test each word separately. If one word is a glyph both readers disagree on, only that one word is unjudgeable — not the entire ending section.

**What is a UTF-8 BOM?**


UTF-8 is how computers store text. A BOM (Byte Order Mark) is three hidden bytes that some text editors put at the very start of a file as a label saying "this file is UTF-8." Most software ignores it or strips it silently.


`clean.py` reads files without telling Python to expect a BOM. Python passes it through as if it were a normal character. Then `clean.py` writes the cleaned markdown with the BOM sitting right at the start of the body content — after the frontmatter header — as an invisible character. It's there in 21 files. For most purposes harmless. For anything doing exact text comparisons, annoying.

Close but not quite. RLVR stands for **Reinforcement Learning from Verifiable Rewards** — not recursive.


The distinction matters. Here's what it actually means:


The dominant way to train AI models used to be RLHF — Reinforcement Learning from Human Feedback. Humans rate which output is better, the model learns from those ratings. Problem: human ratings are subjective, inconsistent, and gameable. A model can learn to produce outputs that *sound* right to a rater without actually being correct.


RLVR replaces the human rater with an objective checker. You only train on problems that have provably correct answers — math, code, logic puzzles. Did the math answer match? Did the code pass the tests? Yes or no, verifiably, no human judgment needed. Because the reward signal is objectively checkable, the model can't fake its way through. Either the answer is right or it isn't.


DeepSeek-R1 was one of the high-profile papers that used this approach and got unusually strong reasoning performance from it.


How it connects to what the checker was doing: the README used "RLVR" not as a literal training technique but as a principle. The idea being — a PASS verdict from the checker is only worth anything if the check itself is verifiable and independent. If the same tool that cleaned the files also checks them, the PASS is like a human rater who already knows the "right" answer — it's not trustworthy. The checker has to be structured so a skeptic can look at the method and confirm the finding independently. That's the RLVR principle applied to document verification rather than model training: the reward (a passing verdict) is only real if it's verifiable.

2. Red agent / cross-auditor verifies each output — pass or fail
3. Verified pairs accumulate in a dataset (locally or direct to Cloud Storage)
4. At threshold or schedule, GCP pulls the dataset and runs a fine-tuning job
5. Updated weights get pushed back to the home node
6. Local model is now slightly better at the types of tasks it was verified on
7. Repeat

**What RLVR actually needs**


Three things: a model whose weights you can modify (not a hosted API — local open-weights models only), a verifiable reward signal (something that can objectively say correct/incorrect), and a training loop to update those weights based on the signal.


Your cross-auditor / red agent architecture is literally a verifiable reward signal.
