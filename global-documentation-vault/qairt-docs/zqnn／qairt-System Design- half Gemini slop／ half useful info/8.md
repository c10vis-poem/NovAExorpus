Yes. Qualcomm, Google, and major open-source engineering teams
explicitly design multi-process, shared-memory backends for mobile AI
inference.

When you scale up to models like **Qwen 3.5 9B**, you run directly into
a severe physical limitation known as the **Inference Memory Wall**.
Stuffer architectures that pool multi-backend frameworks (GGUF, QAIRT,
TFLite) inside a single Android application process space will run out
of memory, crash via the OS kernel, or cause severe thermal throttling.
\[1, 2, 3\]

Three production-grade documentation references prove this exact
architecture is deployed in the wild:

## **1. Qualcomm Official Source: Qairt-AppBuilder & QNNContextProc**

Inside Qualcomm’s official developer utilities repository
([<u>quic/ai-engine-direct-helper</u>](https://github.com/quic/ai-engine-direct-helper)),
Qualcomm's platform engineers explicitly decoupled the NPU runtime out
of standard app boundaries using a multi-process architecture. \[4\]

They expose a highly optimized API built exactly for your daemon
topology: \[4\]

- **QNNContextProc**: A specialized Qualcomm runtime instance
  > specifically engineered to **load and execute AI graphs inside a
  > completely separate system process**. \[4\]

- **QNNShareMemory**: Qualcomm's accompanying native library designed to
  > map memory allocations directly between the application host process
  > and the detached inference processes using physical Inter-Process
  > Communication (IPC). \[4\]

By leveraging this structure, Qualcomm isolates the heavy memory burden
of models like Qwen from the user interface process, using native memory
handles to communicate token streams.

## **2. Google Android Official Source: AICore System Service**

Google’s upstream Android team migrated their entire internal on-device
AI ecosystem to a carbon-copy of the daemon orchestrator pattern you are
pursuing. \[3, 5\]

According to the official Google Android System Architecture
documentation, Android uses a centralized system daemon framework called
**AICore** to serve on-device models. \[3, 5\]

- **Centralized Memory Management**: Models like *Gemini Nano* or custom
  > client models are loaded inside an isolated background system
  > process managed entirely by AICore. \[5\]

- **Zero-Copy Execution Pools**: When an Android app requests text or
  > image generation, it doesn't load model weights into its own heap.
  > Instead, Google creates an anonymous **Shared Memory Layer**. The
  > application UI simply interfaces with a memory pointer, allowing the
  > background AI system daemon to populate tokens directly into the
  > app's buffer space. \[5\]

## **3. Open-Source Source: llama.cpp Native Qualcomm Hexagon Backend**

If you want explicit proof of this running with raw GGUF assets on
Qualcomm chips, look at the upstream engineering work in the
[<u>Official llama.cpp Snapdragon Backend Reference
Documentation</u>](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/developer.md).
\[6, 7\]

Qualcomm engineers natively integrated their hardware into llama.cpp by
splitting the inference binary footprints: \[1, 7\]

- **libggml-hexagon.so**: The regular, decoupled CPU-side orchestration
  > helper layer.

- **libggml-htp-vXX.so**: An isolated, core-specific native library that
  > serves as the operator dispatcher, pushing matrix math tasks cleanly
  > over to the Hexagon Tensor Processor (HTP) based on the device's
  > chip layout (e.g., V73 for Snapdragon 8 Gen 2, V75 for Snapdragon 8
  > Gen 3). \[7, 8\]

Community benchmarks show that compiling these libraries as modular
native subsystems allows running massive models (even up to 12B
parameters) locally on device while staying cool and running
efficiently. \[1\]
