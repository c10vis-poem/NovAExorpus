To support TFLite, GGUF (via QAIRT or llama.cpp), C++, and Rust in a
single pluggable orchestrator, you must build a **native core
architecture** using a C-compatible Foreign Function Interface (FFI).

If you try to orchestrate this directly in Kotlin/Java, your application
will bog down in JNI Marshalling boilerplate, and adding new backends
will break cross-platform portability.

The ideal industry pattern is to write the orchestrator engine core in
**Rust** or **C++**, compile it as a unified shared library (.so), and
let Kotlin/Java simply act as a shallow UI frontend shell.

## **2. The Core Native Interface (C-ABI)**

Rust excels at bridging C++ libraries (like QAIRT and TFLite) to
Java/Kotlin safely via the **Java Native Interface (JNI)** or
**UniFFI**. \[1\]

Define your core orchestrator engine in Rust using standard C-ABI
mappings so both C++ runtimes and Kotlin can interact with it without
data copying overhead:

> *// src/lib.rs*  
> use std::ffi::{CStr, CString};  
> use std::os::raw::{c_char, c_void};  
>   
> \#\[repr(C)\]  
> pub enum BackendType {  
> QairtHtp = 0,  
> LlamaCppGguf = 1,  
> TfLite = 2,  
> }  
>   
> *// Global Orchestrator State managed safely inside Rust*  
> pub struct Orchestrator {  
> active_backend: BackendType,  
> *// Add runtime engine pointers here*  
> }  
>   
> \#\[no_mangle\]  
> pub unsafe extern "C" fn orchestrator_create() -\> \*mut c_void {  
> let orch = Box::new(Orchestrator { active_backend:
> BackendType::QairtHtp });  
> Box::into_raw(orch) as \*mut c_void  
> }  
>   
> \#\[no_mangle\]  
> pub unsafe extern "C" fn orchestrator_load_model(  
> engine_ptr: \*mut c_void,  
> backend: i32,  
> model_path: \*const c_char  
> ) -\> i32 {  
> let \_orch = &mut \*(engine_ptr as \*mut Orchestrator);  
> let path = CStr::from_ptr(model_path).to_str().unwrap_or("");  
>   
> match backend {  
> 0 =\> { */\* Route path to Qualcomm QAIRT C++ loading binaries \*/* 0
> },  
> 1 =\> { */\* Route path to Llama.cpp raw GGUF context loads \*/* 0
> },  
> 2 =\> { */\* Route path to TFLite C++ Flatbuffer Interpreter \*/* 0
> },  
> \_ =\> -1 *// Unknown backend error*  
> }  
> }

## **4. Zero-Overhead Memory Mapping (Zero-Copy Data Transport)**

When running heavy models like a **Qwen 3.5 9B** or complex **TFLite
graphics models**, passing raw byte strings or memory segments back and
forth across Kotlin ⇄ Rust ⇄ C++ will instantly run out of memory or
thermal-throttle the SoC.

Enforce a **Memory File Descriptor (ashmem/memfd)** allocation loop
inside the Orchestrator layout:

1.  **Allocate Memory in Android:** Allocate a direct byte chunk in
    > Kotlin using ByteBuffer.allocateDirect(). This creates memory
    > space outside the standard garbage collected Java heap.

2.  **Pass Address Pointer Natively:** Pass the direct memory pointer
    > memory address directly to the Rust orchestrator via JNI.

3.  **Hardware Zero-Copy:** Rust safely hands off this raw address
    > straight into the QAIRT Tensor layer or TFLite's
    > Interpreter::tensor() array.

4.  **Result:** The NPU writes token outputs right into the space that
    > Kotlin reads. Zero copy cycles occur during background inference.
