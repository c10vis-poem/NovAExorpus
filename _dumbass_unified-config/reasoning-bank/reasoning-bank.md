# reasoning-bank — Repository Reference

Source: `/home/user/reasoning-bank`. Category: **research doc / memory-pattern reference** (academic code release, not an app — the reusable asset is the retrieval *pattern*, not the code).

## 1. What it is

Official research code release for **"ReasoningBank: Scaling Agent Self-Evolving with Reasoning Memory"** (Ouyang et al., Google, submitted to ICLR 2026). No `CLAUDE.md`/`AGENTS.md`/`docs/` — the README is the only top-level documentation.

"Reasoning bank" here means: **a memory mechanism that distills natural-language "memory items" (insight/strategy summaries) from both successful and failed agent trajectories, stores them in a bank, and retrieves relevant ones at inference time to prime a fresh agent run.** Not a database/vector-store product — an experimental harness for two benchmarks (WebArena web-browsing agents; SWE-bench/mini-swe-agent software-engineering agents) implementing ReasoningBank plus two baselines for comparison (AWM = "Agent Workflow Memory", Synapse = raw trajectory storage), plus a "memory-aware test-time scaling" extension (parallel-trajectory self-contrast).

## 3. Core data model

No schema file/ORM/DB — memory is plain **JSONL on disk**. A memory-bank record:

```json
{
  "task_id": "47",
  "query": "<user intent/task description>",
  "think_list": ["..."], "action_list": ["..."],
  "status": "success" | "fail",
  "memory_items": ["# Memory Item 1\n## Title ...\n## Description ...\n## Content ...", "..."],
  "template_id": "<task template id for dedup>"
}
```

Each **memory item** is a small Markdown block with three fields — `Title`, `Description` (when/when-not to use it), `Content` (1-3 sentences of actionable insight) — generated by an LLM call using prompts `SUCCESSFUL_SI`/`FAILED_SI`/`PARALLEL_SI` (`WebArena/prompts/memory_instruction.py`). At most 3 items per trajectory (5 for the parallel/self-contrast variant), explicitly asked to be generalizable/abstract rather than embedding literal task strings.

Embeddings cached separately: `{"id": task_id, "text": query, "embedding": [floats]}` in parallel JSONL files.

## 4. Retrieval mechanism

Purely **embedding-based cosine similarity**, no keyword/tag search. `select_memory()`/`screening()` in `WebArena/memory_management.py`: embeds the current query with Gemini (`gemini-embedding-001`, 3072-dim, Vertex AI) or a local Qwen3-Embedding-8B model → wraps in a domain-tailored instruction template → dot product against all cached embeddings → top-`n` (capped at 10, default `n=1` in practice) matches by `task_id`. Every new query embedding is appended to the cache as a side effect. SWE-Bench side (`third_party/src/minisweagent/memory/memory_management.py`) is essentially a duplicate implementation.

## 5. Agent/LLM integration

No MCP server, no REST API, no distributed CLI — integration is by direct import within each benchmark runner. WebArena's `run.py` writes retrieved memory to a flat `.txt` that `Memory` class (`use_memory` flag) renders into a `<memory>...</memory>` prompt section. SWE-Bench's `swebench.py` calls `select_memory` then passes `selected_memory=...` into `DefaultAgent.run()`, appended onto the system prompt with an instruction to "discuss if you want to use each memory item." Supports GPT-3.5/4/4o, Gemini 2.5 Flash/Pro, Claude 3.7 Sonnet via Vertex AI.

## 6. Skills/plugin architecture

None. Closest analog is the `--memory_mode` switch (`reasoningbank`/`awm`/`synapse`/`no_memory`) — a simple string-dispatched strategy swap, not a discoverable plugin system.

## 7. Testing/tooling

No test suite, no CI. Tooling is `uv` (lockfile, pinned Python version) plus shell scripts hardcoding env vars. `.gitignore` excludes generated artifacts (`config_files/`, `results*/`, `logs*/`, `memories_reasoningbank/`), confirming these are runtime-generated.

## 8. What's actually reusable here

Not the code (research harness, benchmark-specific, no server/API). The reusable ideas:
- **Memory-item schema**: Title / Description (when to use) / Content (actionable insight), kept short and generalizable rather than literal.
- **Learn from failure too**: distilling insight from failed trajectories, not just successes — a pattern OB1's `thoughts` table doesn't currently do (it just stores captured thoughts, no success/fail framing).
- **Retrieval by embedding similarity to the *current task*, capped small (n=1-10)** — a lighter-weight retrieval philosophy than broad semantic search over everything.
